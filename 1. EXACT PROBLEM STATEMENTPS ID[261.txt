EXACT PROBLEM STATEMENTPS ID[26151]Exact Problem StatementDark web threat actor de-anonymization• Background: The dark web has become a preferred operating space for threat actors in the modern age, mainly because it lets them hide their identity behind Tor hidden services, which makes attribution of threat actors operating on darkweb the main challenge for any investigation. Such threat actors carry out a wide range of unlawful activities such as drugs and arms sale, stolen data and hacking services, money laundering, terror financing, etc. The objective of this problem statement is to build a system for the deanonymization of dark web threat actors and link them to suspect real-world entities.• Description: The system shall deanonymize dark web threat actors by continuously gathering their footprints from a range of sources (marketplaces, forums, deep web etc.) and linking them to the identifying information available on those sources. The system envisages three core capabilities. First, finding misconfigurations in Tor hidden services—such as exposed server-status pages, SSL certificates tied to clearnet domains, default service banners, descriptor inconsistencies, etc and matching them with clearnet infrastructure to point to the likely origin servers. Second, mapping threat actors across multiple marketplaces into a single relationship graph of handles, PGP keys, wallets and trust links. Third, using AI-based analysis, including stylometric persona identification and behavioural profiling, to link rebranded or migrated personas to known threat actors. The system shall provide an analytical front end to query the database across a chosen timeline and shall work in an autonomous mode, drawing on available sources of good quality and reliability.• Expected Solution: An end-to-end system shall be developed for the collection, storage, contextualization and querying (through GUI/dashboards) of dark web threat actor intelligence—covering actor profiles, identifiers (handles, PGP keys, wallets etc.), hidden service infrastructure indicators, persona linkages, attribution confidence, category, last scan date and source. The system shall also provide the facility to export the result set in CSV, JSON and report formats.Answer:What is the PS actually asking us to solve? NTRO wants a centralized intelligence platform (a unified OSINT/threat-intel tool) that scrapes the Dark Web (Tor), analyzes technical mistakes made by server admins, tracks cryptocurrency and PGP footprints, and uses AI to analyze writing styles. The goal is to unmask anonymous criminals and connect their different fake identities to each other and eventually to their real-world identities.What does each important sentence mean?Continuous gathering: Needs automated web scrapers routed through Tor.Misconfigurations: Finding technical flaws (like a server accidentally revealing its real IP address or using a public SSL certificate on a hidden service) to locate the physical server.Mapping actors: Using Graph databases to link a user on Market A to a user on Market B because they used the same Bitcoin wallet or PGP encryption key.AI-based stylometric analysis: Using NLP to prove "HackerX" is the same person as "VendorY" based on how they type, spell, and use grammar.What is the actual problem behind the wording? Law enforcement currently does these steps manually or uses highly fragmented, expensive tools. There is no single open/custom platform that combines infrastructure scanning, graph mapping, and AI linguistics specifically tailored for Indian intelligence agencies.Why does this problem exist? Tor is designed to make tracing impossible by bouncing traffic. Criminals use Tor to operate with impunity.Who is facing this problem? Intelligence agencies (NTRO, RAW, IB), cyber police, and national security organizations.Who is responsible for solving it today? Cyber threat intelligence analysts, OSINT researchers, and specialized law enforcement units.What happens if this problem remains unsolved? Threat actors continue to sell drugs, weapons, and stolen national data without fear of arrest.What outcome does the organization actually want? A dashboard where an analyst can type a username like "DarkLord" and instantly see their connected Bitcoin wallets, their other usernames across 5 different forums, the real IP address of their hidden server (if misconfigured), and a confidence score that they are the same person.What would a successful solution look like? An automated backend engine doing continuous Tor crawling, a Neo4j (or similar) graph database connecting the dots, an AI model scoring writing styles, and a React/Angular frontend displaying intelligence graphs.Findings:A. Explicitly stated by the PS: Must use AI stylometry, must build a relationship graph (PGP/Wallets/Handles), must scan for Tor misconfigurations (SSL/Server-status), must export to CSV/JSON.B. Reasonable inference: The system requires managing Tor proxies to avoid bans, requires a graph database, and needs integration with clearnet datasets (like Shodan/Censys) to match SSL certificates.C. Things that need further research/verification: How to continuously scrape dark web marketplaces without getting blocked by their anti-bot protections (captchas, login walls).2. REAL-WORLD PROBLEMWhat is happening today? Threat actors operate on Dark Web forums (like Exploit, XSS, or former markets like AlphaBay/Silk Road equivalents). They frequently change usernames (rebranding) when a market is shut down by police.Who experiences the problem? Intelligence analysts who have to manually read thousands of forum posts to figure out if a new threat actor is actually an old, known criminal.How frequently does it happen? Daily. The Dark Web ecosystem is highly volatile; markets close and open constantly, causing mass migrations of users.Why is it difficult? The Dark Web has no central search engine. Sites go offline randomly. Threat actors use operational security (OpSec) to hide.What causes it? The cryptographic routing of the Tor network hides IP addresses, and cryptocurrencies pseudo-anonymize finances.What are the consequences? Delayed investigations, unpunished cybercrimes, and national security threats.What resources are currently wasted? Thousands of human man-hours spent manually tracking PGP keys, comparing forum posts, and running individual Python scripts to check server status.Where do delays occur? Manually correlating a Bitcoin wallet found on a Dark Web forum with a clearnet exchange.Where do errors occur? Assuming two actors are different people because they use different usernames.Where is human intervention required? Connecting technical evidence (IPs/Certs) to behavioral evidence (writing style).Where does data become unavailable, duplicated, outdated, or incorrect? Dark web sites frequently undergo DDoS attacks or change onion addresses, making static links dead.Simple Example:A hacker named "Shadow99" sells stolen Indian credit cards on Dark Market A. Market A gets seized by the FBI. Two weeks later, a new user named "NightRider" appears on Market B selling similar credit cards.Currently, an analyst has to manually check if NightRider uses the same PGP key or Bitcoin wallet as Shadow99. If they don't, the trail goes cold.With our system: The AI reads NightRider's posts, notices he uses the exact same rare grammatical errors and slang as Shadow99. The system also notices NightRider's Tor server accidentally exposed an SSL certificate that maps to a real IP address in Eastern Europe. The analyst is instantly notified.3. 1. PS Understanding — What is NTRO actually asking?

The PS has three major attribution pillars:

Pillar A — Infrastructure attribution

Find technical information accidentally exposed by an onion service and correlate it with clearnet infrastructure.

Examples mentioned by the PS:

exposed server-status pages
SSL/TLS certificates
default server banners
configuration inconsistencies
infrastructure fingerprints
clearnet domains/IPs
reused hosting infrastructure

The goal isn't simply:

.onion → IP

It is closer to:

.onion → technical fingerprint → candidate infrastructure → corroborating evidence → attribution confidence

This distinction is extremely important.

Tor onion services are specifically designed to hide the service's location/IP address. Modern v3 onion services also use cryptographic mechanisms to protect descriptors and introduction information.

Therefore, breaking Tor cryptography is not the intended solution.

The opportunity is finding operator mistakes, reused infrastructure, public metadata and cross-source correlations.

2. Pillar B — Cross-marketplace Actor Mapping

Suppose the same actor appears as:

Forum A
username = ShadowX

Marketplace B
username = XShadow

Forum C
PGP key = ABC123

Marketplace D
wallet = bc1....

Telegram
handle = ShadowX

Individually, these aren't necessarily enough.

But together:

   |

   |
   +---- Wallet

   |
   +---- Vendor profile
   |
   +---- Forum account

can form an actor relationship graph.

This is essentially an entity-resolution problem.

3. Pillar C — AI-based Persona Analysis

The third component is much more interesting.

The system should ask:

Signals could include:

Academic research has specifically explored stylometry for linking users who migrate between darknet forums. The SYSML research reported improvements over prior approaches on its evaluated datasets, but this should be treated as research evidence rather than proof that stylometry can identify a real person.

There is also important contrary evidence: research on darknet-market vendors found stylometry can be difficult when descriptions are short and repetitive.

So your system should never say:

“AI identified the criminal.”

It should say:

“The available evidence produces an X% attribution confidence, with these supporting and contradictory indicators.”

That's a much more defensible design.
